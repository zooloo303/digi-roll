S0

Confirm the box identifies correctly

human
  1. Plug the Digitone 1 into USB, load a scratch project — never a live set (CLAUDE.md's rule, same as every other device here).
  2. Open difflab.html, pick the DN1's port, Connect.

Expect: the device info line reads “Digitone” (not “Elektron device #20” — that would mean the product-id registration in device.js is wrong) and the family byte shows 0d. If it instead says “Digitone II”, slugFromPortName's longest-name-first match broke — stop and say so, that's a code bug, not a hardware finding.

Trig conditions — the one blocking unknown needs S0

The DN1 stores COND/FILL/PROB as one combined byte per step (unlike the DT2/DN2's three separate lanes digi-roll already decodes). Nothing ships for DN1 conditions until this table exists — see dn1-support-plan.md §1. Walk the menu one entry at a time; each entry is its own capture pair.

C1

Baseline, then one trig with no condition

human
  1. Capture baseline on an empty pattern.
  2. Add one note trig, track 1, step 1. Leave TRC/condition unset.
  3. Capture + diff, note “trig added, no condition”, Save to notebook.

Expect: confirms the byte at track-relative 0x140 (this module's track.trigCondition) reads 0xFF on an unconditional trig, matching the DT2/DN2 "none" sentinel.

C2

Walk the condition menu, one step at a time

human
  1. Chain: B → baseline from C1's capture.
  2. Open that trig's TRC page. Set it to the first entry in the menu (whatever the DN1 shows first — note the exact on-screen label in the note box).
  3. Capture + diff, note the exact label shown on the box, Save, then Chain: B → baseline.
  4. Move to the next entry in the menu. Repeat capture/save/chain.
  5. Continue through the whole menu — expect roughly 20–35 entries, going by the DT2/DN2 COND list's size and DNX's DN1 corpus, which saw 35 distinct byte values in the wild.

Expect: one byte value per on-screen label, monotonically or in whatever order the menu actually shows — do not assume it matches the DT2/DN2 order (js/elektron/conditions.js); that table's own header says it was walked by hand for exactly this reason. Percentages (PROB) and FILL are believed to live in this same menu on the DN1, unlike the DT2/DN2's separate lanes — confirm that as you walk it, and flag immediately if a percentage or FILL entry doesn't fit the single-byte model.
This is the long one. It's fine to split across sessions — Export pair after each handful and the notebook survives a reload.

Export the condition notebook

agent
  1. Once C2 is walked, Export .md from the notebook pane.

Swing — a strong candidate, not yet a fact needs S0

SW1

Move pattern swing and diff exactly one byte

human
  1. Capture baseline on any pattern at the default 50% swing.
  2. Set swing to 80% (the DT2/DN2 max) — the DN1's swing setting is per-pattern, same menu location as the DT2/DN2.
  3. Capture + diff, note “swing 50→80”, Save.

Expect: exactly one byte changes, at pattern offset nameOffset + 24 (0x473C) — the same relative offset the DT2/DN2 swing byte sits at. This offset already reads a plausible value in five real captures this session (0 in 504 of 516, 4 in the rest — dn1-support-plan.md §1) but that's corpus evidence, not a controlled edit. If more than one byte moves, or a different offset, stop — that means the DT2/DN2 analogy doesn't hold and pattern-settings.js's DN1 wiring needs to change before Phase 2.

Chords — offset direction and ordering needs S0

CH1

A 4-note chord on one step

human
  1. Capture baseline on an empty pattern.
  2. Enter a 4-note chord on track 1 step 1 through NOTE EDIT — e.g. C4, E4, G4, B4 (a Cmaj7).
  3. Capture + diff, note the exact notes entered and the order you pressed them, Save.

Expect: byte 0 of the 8-byte note record (track-relative 0x180 + 8×step) is the lowest pitch (root), and the other three are signed offsets from it — this module's encoder assumes exactly that (lowest pitch is root; see js/elektron/dn1/pattern.js's encodeTrackNotes) but it's inferred from DNX's corpus, not confirmed by an entry on real hardware. If the root isn't the lowest note — if it's whichever note was pressed first, say — that assumption is wrong and needs fixing before any DN1 write path.

Track length needs S0

TL1

Change one track's length and diff the settings tail

human
  1. Capture baseline on a track at its default 16-step length.
  2. Change that track's length to 32 steps.
  3. Capture + diff, note “track 1 length 16→32”, Save.

Expect: one byte changes at track-relative 0x3C0 + 0x0C (settings +12), reading 32. This is DNX's INFERRED reading, untested on real hardware — confirming it also unblocks trusting track.lengthSteps for the fallback used when a note's length byte reads 0x7F (infinite).

Step-flag mystery bits needs S0, lower priority

FL1

Retrig, if the DN1 has one on a note trig

human
  1. Capture baseline with one plain note trig.
  2. Turn retrig on for that trig, if the DN1's UI offers it per-trig.
  3. Capture + diff, note exactly what was turned on, Save.

Expect: one of the unexplained step-flag bits (0x0080, 0x0200, 0x0400, 0x2000, 0x4000 — DNX §4.1) lights up. Retrig is the standing guess; this is the cheapest way to test it. Not blocking — digi-roll's encoder already preserves every step-flag bit it doesn't understand, so this is purely upside, not a prerequisite for anything in the plan.

Write path Phase 2 — needs Phase 0 conditions done and Phase 1 code merged first

W1

Null round trip: read a pattern, write it back to itself

human
  1. Scratch project. Note which pattern slot is loaded.
  2. Fetch the pattern, re-send the identical bytes to the same slot, fetch again, byte-compare.

Expect: byte-identical, the same "the write path works and changed nothing" proof DNX ran first on this exact box (docs/device-probing.md §"WRITING WORKS"). Only after this passes is WRITE_ALLOWED_BUILDS.digitone worth adding, and only for the exact build string this ran against.

W2

Write a real track, verify, then check the box's own UI

human
  1. Empty pattern slot on the scratch project.
  2. Draw a short pattern in digi-roll's roll (notes + a chord), Send to box, let the safe-write flow back it up, write, and verify.
  3. Look at the box: right notes, right chord, right slot, nothing else changed. Play it.

Expect: verify reports byte-identical, and the box agrees by ear and by screen. Also worth trying deliberately: write to a slot that already has work on it, per DNX's finding that the DN1 silently refuses a write to an occupied slot rather than overwriting (docs/device-probing.md) — if digi-roll's verify then reports "did not store what we sent" for a refusal rather than a real corruption, that's the three-way comparison (dn1-support-plan.md Phase 2) worth building before this ships.
