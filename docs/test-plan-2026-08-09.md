### A1. The diff lab survives a malformed donation — **pre-run, passed**

This is the highest-severity fix: before it, one bad notebook entry killed the
page *before* MIDI init, and the delete buttons that would have removed it were
rendered by the function that threw. The only escape was clearing storage.

First generate two malformed-but-legitimate donation files. (The obvious way to
make one — flipping a byte in the built SysEx — produces a checksum failure that
`parseCapturePair` rejects before it reaches the code under test. This generator
re-encodes properly, so the files exercise the real path.)

```js
// /tmp/make-test-pairs.mjs — run with: node /tmp/make-test-pairs.mjs
import { readFileSync, writeFileSync } from 'node:fs';
import { splitSysExStream, buildDumpMessage, DUMP, FAMILY }
  from '/Users/neilward/Projects/digi-roll/js/elektron/protocol.js';
import { buildCapturePair }
  from '/Users/neilward/Projects/digi-roll/js/labs/capture-pair.js';

const kits = splitSysExStream(new Uint8Array(readFileSync(
  '/Users/neilward/Projects/digi-roll/dumps/digitakt2-project-2026-08-01T23-37-04.syx')))
  .filter(m => m.kind === 'dump' && m.type === DUMP.PATTERN_KIT);

const basePayload = kits[0].payload;
const after = Uint8Array.from(basePayload);
after[5000] ^= 0x0f;

const raw = p => buildDumpMessage(FAMILY.DIGITAKT_2, DUMP.PATTERN_KIT, 0, p);
const text = buildCapturePair({
  device: { name: 'Digitakt II', productId: 42, build: '0070', version: '1.15B', slug: 'digitakt2' },
  family: FAMILY.DIGITAKT_2, requestType: 0x60, index: 0,
  note: 'test-plan donation', capturedAt: '2026-08-09T10:00:00.000Z',
  baselineRaw: raw(basePayload), afterRaw: raw(after),
});

const noDevice = JSON.parse(text); delete noDevice.device;
writeFileSync('/tmp/pair-no-device.json', JSON.stringify(noDevice, null, 2));
const junkDevice = { ...JSON.parse(text), device: { name: 5, build: { odd: true } } };
writeFileSync('/tmp/pair-junk-device.json', JSON.stringify(junkDevice, null, 2));
```

**A1a — the original brick, end to end.** Open `difflab.html`, click *Open
pair…*, choose `/tmp/pair-no-device.json`. Expect the diff to render and the
capture line to read `… · unknown device`. Click *Save to notebook*, then
**reload**.

- ✅ Page boots to `Pick your box and hit Connect.` (i.e. it got past the
  notebook to MIDI init).
- ✅ The entry renders, meta line `unknown device · A01 · 2026-08-09 10:00:00`.
- ❌ Any uncaught TypeError in the console, or a status line stuck empty.

Repeat with `/tmp/pair-junk-device.json` — non-string junk must coerce, not
propagate.

**A1b — hostile notebook entries.** In the console:

```js
localStorage.setItem('digiroll-difflab-v1', JSON.stringify([
  { note: 'no device block', index: 0, at: '2026-08-09T10:00:00Z',
    ranges: [{ start: 1, end: 2, label: 'x', was: '00', now: '01' }] },
  null,
  { note: 'no ranges array', device: 'Digitakt II', version: '1.15B', build: '0070',
    index: 3, at: '2026-08-09T10:00:00Z' },
  { note: 'no at / no index', device: 'Digitone II', ranges: [] },
]));
```

Reload. Expect all four to render, the `null` as
`(unreadable notebook entry) … — the ✕ removes it`, and **four ✕ buttons**. Click
the ✕ on the stub: it must actually disappear and drop out of localStorage. That
escape hatch is the point — a bad entry must always be removable from the UI.

**A1c — corrupt storage.** `localStorage.setItem('digiroll-difflab-v1', 'not json')`,
reload. Expect `No experiments saved yet.` and a working page, not a dead one.

Clean up: `localStorage.removeItem('digiroll-difflab-v1')`.

### A2. The backup stash holds a real pattern — **pre-run, passed**

The unit tests use 64-byte payloads; a real pattern kit is 111,616 bytes, and
four of them base64'd is the actual storage question.

On any served page:

```js
const m = await import('/js/elektron/backup-stash.js');
for (let i = 0; i < 6; i++) {
  const payload = new Uint8Array(111616);
  for (let j = 0; j < payload.length; j += 997) payload[j] = (i * 31 + j) & 0xff;
  m.stashBackup({ slug: 'digitakt2' }, { index: i, name: `kit-${i}.syx`, payload });
}
const back = m.stashedBackups('digitakt2');
console.log(back.length, back.map(e => e.index),
  Math.round(localStorage.getItem('digiroll-backup-stash-v1').length / 1024) + ' KB');
```

**Expected:** `4`, `[5, 4, 3, 2]` (newest first, oldest evicted), **~582 KB**.
Payloads must come back byte-exact.

Note the pressure: 582 KB sits alongside the roll state and the Library bank in
the same origin's ~5 MB budget. If a big bank ever pushes it over, `stashBackup`
returns false and the write log says so — worth confirming that message reads
sensibly if you ever see it.

Clean up: `localStorage.removeItem('digiroll-backup-stash-v1')`.

### A3. Notes joining an occupied step take that trig's conditions

The invariant: PROB/FILL/COND are per *trig*, so notes sharing a step must
agree. When they didn't, the encoder silently believed the lowest-pitch note, so
a pasted `2:4` could vanish on write with nothing said.

On `index.html`, in one pattern slot:

1. Draw a note at step 4. In the trig lane below the grid, give it **COND 2:4**
   and **PROB 40**.
2. Draw a plain note at step 12, no conditions.
3. Select the step-4 note, copy, click step 12's cell to set the caret, paste.
   - ✅ The pasted note shows **no** conditions (it joined step 12's unlocked
     trig), and the status line says `… joined an existing trig and took its
     conditions`.
4. Undo. Now drag the step-12 note **onto step 4**.
   - ✅ It picks up 2:4 / 40, and the status line says so.
5. Alt-drag a copy of the step-4 note onto step 12, then alt-drag one onto a
   note that already sits on an occupied step — same adoption, same message.
6. **Regression guard:** set a condition with the trig lane on a step holding a
   chord, then nudge one chord note's velocity (shift-drag) and its micro
   (cmd-drag). The condition must survive — the trig lane already writes across
   every note on a step, so adoption should be a silent no-op here, with **no**
   status message.

The lowest-pitch rule is what the encoder uses, so step 4 above should adopt from
its lowest note if it holds several.

### A4. A p-lock lost to a move is announced

1. Add a p-lock lane (e.g. FLTR CUTOFF) and draw values on the steps under two
   or three notes.
2. Drag one of those notes to an empty step.
   - ✅ The lock does **not** follow (locks are step-scoped, matching the box),
     and the status line says `N p-lock value(s) cleared from steps that lost
     their trig`.
3. Delete a note carrying a lock — same message.
4. Shorten the pattern (the Length menu) so it drops notes carrying locks — same
   message.
5. **Regression guard:** a read-only lane (one imported from a box, drawn dimmed
   and hatched) must **never** be pruned or counted — it's passed back byte-exact.

If the "locks should follow a moved note" behaviour is wanted instead, that's a
design change, not a bug fix — note it and leave it for a later round.

## Part B — hardware, both boxes

**Throwaway project only.** Load a scratch project on each box before starting;
nothing here should point at a live set. Rule 5 is the backstop for everything
else in this plan.

`safe-write.js` changed this round, so the ordinary write path needs a
regression pass even though its logic is unchanged.

### B1. The ordinary write path still lands (regression)

On each box, at the allowlisted builds (DT2 `0070`, DN2 `0049`):

1. Draw a few notes with mixed conditions, a track PROB, one p-lock lane and a
   non-default swing. Send to a blank pattern from the **main page**.
   - ✅ Backup downloads, confirm dialog names conditions / PROB / lanes / swing,
     write verifies byte-identical.
   - ✅ The box's own UI shows what you drew.
2. Repeat from the **console's Write to pattern** row.
3. Repeat from the console's **Copy track** row (DN2 → DT2, the direction
   already verified 2026-08-04).

Any verify mismatch here is a stop-the-line result — it would mean the stash
insertion disturbed the write sequence.

### B2. Restore, the genuinely new hardware behaviour

This is the one path that never existed in this form: it used to be a bare
`sendPatternKit`.

1. **Restore after a write.** Write a track (B1 step 1), then hit *Restore*.
   - ✅ The confirm names the backup and says the slot's current contents
     download first.
   - ✅ A `pre-restore` .syx downloads — check it's the *botched* state, not the
     bytes being restored. That file is the evidence if a restore goes wrong.
   - ✅ Status reads `restored from backup — verified`; the box's UI shows the
     original track back.
2. **Restore from the stash, after a reload.** Write a track, then **reload the
   console page** and reconnect.
   - ✅ *Restore* is enabled even though `lastBackup` is gone — it's reading the
     stash.
   - ✅ The confirm includes `(stashed <timestamp>)`.
   - ✅ Restore verifies, and the box shows the pre-write state.
3. **Cross-page stash.** Write from the **main page**, then open the **console**
   and connect.
   - ✅ *Restore* offers that backup (the stash is shared across pages, keyed by
     box slug).
4. **The gate re-check.** Hard to trigger honestly without an OS change — cover
   it by confirming *Restore* is disabled with no box connected, and that
   connecting a box digi-roll can't write to leaves it disabled with the reason
   shown.
5. **Wrong-box guard.** With a DT2 connected, confirm the stash offers only DT2
   backups (take a DN2 backup first, then reconnect the DT2). A DN2 pattern
   restored onto a DT2 would be a serious write.

### B3. Backup-failure behaviour (optional, worth doing once)

Set Chrome to block automatic downloads for `localhost`, then write a track.

- ✅ The write still proceeds (the stash copy exists), and the log line says a
  copy is stashed in the browser.
- ✅ *Restore* can put the slot back **from the stash alone**, with no file ever
  having reached disk.

That is the whole point of fix #2 — before it, this scenario left you with a
modified pattern and no backup at all.

## Known gaps this plan does not close

Carried forward from before this round, and not addressed by it:

- **Swing has never been written to a DT2** — same byte as the DN2, corroborated
  by fixtures, untested on hardware.
- **A DT2 write of a per-slot chord is not hardware-verified**, and whether a DT2
  MIDI track plays each slot's own values is unknown.
- **Cross-device lane copy DT2 → DN2** is untested (the reverse passed
  2026-08-04); it runs the same name-keyed path.
- **Restore's gate re-check** can't be tested properly without an OS build
  change (B2 step 4 is a proxy).
